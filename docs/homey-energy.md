# Native Homey Energy reporting

## Scope and data boundary

The optional native Energy companions provide power and battery SoC, plus an opt-in cumulative-kWh register profile. The declared app minimum is **Homey >=12.4.5** for the separate import/export Energy mappings. It does not replace the existing Sigenergy plant device or the custom Dashboard widget. Native Energy visibility and whole-house totals still require physical validation; keep [issue #37](https://github.com/Marza/homey-sigenergy/issues/37) open.

The [Homey Energy SDK](https://apps.developer.homey.app/the-basics/devices/energy) distinguishes grid metering, solar generation and home batteries. This implementation uses three separate driver roles with standard `measure_power` values, following those roles:

| Optional device | Class / Energy role | Source and sign |
| --- | --- | --- |
| Sigenergy Energy — grid | `sensor`, `cumulative: true` | Existing `gridW`: positive import, negative export; never a derived house-load value |
| Sigenergy Energy — solar | `solarpanel` | Selected `pvW`: own PV (30035), third-party inverter (30194), or their explicit sum; negative/invalid/missing selected components are unavailable |
| Sigenergy Energy — battery | `battery`, `homeBattery: true` | Existing `essW`: positive charging, negative discharging; valid SoC is published separately |

The original plant retains its device ID, class, capabilities, connection settings and history. No existing pairing is removed or replaced. No Energy companion is created automatically. Each companion points to its selected existing plant using that plant's pairing-data ID and only reads the parent's live in-memory snapshot. It opens no Modbus connection, adds no independent register reads and has no command capabilities or listeners. Selecting third-party/combined solar adds one input-register read on the shared connection per plant poll, independently of the kWh profile. Enabling the counter profile adds five optional reads (six for combined solar) to the existing plant loop at most once per minute. No `target_power`, switching, writable battery state or native scheduling is introduced.

Homey can use the selected grid/solar/battery roles to form its native energy overview. We do **not** publish `gridW + pvW - essW` as another whole-house meter: doing so would invite duplicate accounting. AC/DC measurement boundaries, conversion losses, sampling alignment and import/export/charge/island states require independent validation. Direct reporting of these readings therefore does not establish calibrated AC house consumption. Physical comparison of the resulting native flows is a required follow-up.

## Setup after merge, release and installation

1. Keep the existing configured Sigenergy plant device. Check that it is receiving fresh data.
2. In Homey's add-device flow for this app, select **Sigenergy Energy — grid**, **solar** or **battery** and select the parent plant. Each role can be added separately; already-paired parents are omitted for that role. Add only the roles not already reported by another integration.
3. If a P1 meter/Homey Energy Dongle/Tibber meter already supplies grid exchange, retain one authoritative grid source. Likewise choose one solar source and one battery source. This app does not inspect other apps or automatically decide which source is authoritative.
4. Use Homey's native **Exclude from Energy** setting to exclude duplicates. The grid device's native **Tracks total home energy consumption** setting determines its main-meter role. Check native settings before relying on the overview. See the [official Energy settings documentation](https://apps.developer.homey.app/the-basics/devices/energy#settings).
5. Each companion also has an app setting to disable live publication. Disabling clears its current values and marks it unavailable; it does not erase prior Energy history or guarantee that the native UI hides its tile. Remove only an unwanted companion if appropriate; the original plant stays paired.

The SDK driver manager resolves the existing source through [`getDriver`](https://apps-sdk-v3.developer.homey.app/ManagerDrivers.html#getDriver) and [`getDevices`](https://apps-sdk-v3.developer.homey.app/Driver.html#getDevices). Startup order is handled by retrying lookup; the companion never starts a replacement plant reader.

## Freshness and lifecycle

Companions refresh every five seconds, using the existing poll's timestamp and a freshness limit of at least 30 seconds or three configured poll intervals. Thus loss/staleness is reflected by the next companion refresh, not instantaneously. A failed or replaced parent reader clears its snapshot. Source removal, startup without a snapshot, invalid/future/stale timestamps and disabled publication yield unavailable/null, not a fabricated zero. Real measured zero remains zero. Grid reporting is unavailable for island/unknown grid mode; solar and battery may still show independently valid source measurements.

A software plausibility bound rejects power magnitudes above 10 MW; it is not a verified inverter rating. Invalid battery SoC is cleared without inventing a percentage. Capability-write failure attempts to clear readings and mark the companion unavailable. Only one refresh is in flight; source generation, disable and shutdown changes are rechecked around asynchronous writes so old results cannot mark the companion available again. A later refresh can recover. If Homey itself rejects a clearing write, the companion is still marked unavailable where possible; this is not a guarantee about how every native client renders stale cached values.

## Cumulative kWh profile

After merge/release, existing Energy companions acquire the new capabilities with `addCapability` only where missing; pairing IDs and native exclusion settings are preserved. The driver manifest maps separate imported/exported counters for grid and battery, and generated energy for solar, following the [Energy SDK](https://apps.developer.homey.app/the-basics/devices/energy). No automatic profile selection or fallback to another register family occurs.

In the **original Sigenergy plant device's advanced settings**, select **Sigenergy V2.9 new statistics** only after confirming that the installed firmware supports that statistics interface. The default remains **Disabled (power only)**. Select **Solar source (W and kWh) / Solkälla (W och kWh)** separately: own PV, third-party inverter, or both. The existing default is own PV so upgrades do not silently change an established reference. Each optional read uses a one-second response timeout; transport failure stops that batch instead of repeating all selected timeouts. Counter reads are serialized with the shared plant loop and can add latency; they are not a second polling connection. The reader uses the existing connection, input-register function 0x04 and **plant unit 247**. Address offset follows the existing reader setting. Unsupported registers fail independently; they never replace missing energy with zero or fail the fast power snapshot.

The manufacturer-authored **Sigenergy Modbus Protocol V2.9**, released 2026-05-13, table 5-1, printed pages 13–14 (PDF pages 21–22), defines this selected group:

| Quantity | Address | Homey capability |
| --- | --- | --- |
| Own PV generation (excluding third-party inverter) | 30236 | Solar: `meter_power` when own/combined is selected |
| Third-party inverter generation | 30240 | Solar: `meter_power` when third-party/combined is selected |
| ESS charged energy | 30244 | Battery: `meter_power.charged` |
| ESS discharged energy | 30248 | Battery: `meter_power.discharged` |
| Grid imported energy | 30260 | Grid: `meter_power.imported` |
| Grid exported energy | 30264 | Grid: `meter_power.exported` |

These are four-register unsigned 64-bit counters with gain 100 in kWh. The implementation decodes high word first using BigInt, validates before conversion, and keeps integer hundredths in persisted state. Word order and actual counter agreement remain part of physical profile verification. A broad software magnitude ceiling of 10^12 kWh rejects unsupported/sentinel values; it is not a site rating or proof of meter accuracy.

Primary document: [manufacturer PDF mirrored in the reference repository](https://github.com/TypQxQ/Sigenergy-Local-Modbus/blob/main/Modbus_reference_documentation/Sigenergy%20Modbus%20Protocol%20EN_V2.9.pdf). Inspected file SHA-256: `1e4306bcf46735f8432fcec0dae83938fa49107790d02beaf702285961a5d0d8`. The document's note on printed page 14 says the new statistics family starts from zero after firmware enabling it, without inheriting earlier history. The older [V2.5 manufacturer protocol](https://b2b.aprilice.com/se_en/mpattachment/file/download/id/778/), table 5-3, marks 30554–30565 reserved; this implementation does not use those older inverter energy addresses. Document version is not proof that a particular installation supports the profile.

Allow at least two successful counter samples after enabling the profile: the first establishes the native baseline, and this implementation does not supply pre-installation Energy history.

The **Energy counters / Energiräknare** field shows disabled, waiting, current, partial, stale, reset-required, source-changed or invalid. A counter can be unavailable while the companion still reports valid W/SoC. kWh samples older than three minutes are cleared. Counter references are cumulative source measurements, not the prior Tibber month archive, rolling integrated power, daily-reset totals or reconstructed battery savings. Homey must collect differences from valid counter samples; this feature does not backdate native Energy history.

## Third-party solar and source comparison

The V2.9 table explicitly excludes third-party inverter energy from own-PV register 30236. The distinct register 30240 is the third-party component. Selecting **combined** adds both integer counters before applying the solar continuity guard; both reads must succeed. A missing component is not assumed to be zero. Selecting **third-party** reads only that component for solar. The selected source must match the intended installation; no discovery or automatic source switch is claimed. Own PV can legitimately stay zero in a storage system whose solar production is supplied externally.

A previously published own-PV zero must not suddenly become an entire lifetime third-party total in today's Energy report. Changing the source therefore yields `source-changed` and withholds solar publication until **Confirmed solar-source changes / Bekräftade byten av solkälla** is increased by one after verification. This solar-only acknowledgement preserves grid/battery continuity; use the shared counter-reference generation only for an actual broader reset/connection change. It then holds the last published total and counts subsequent measured changes. Published Energy totals may consequently differ from the raw selected-source lifetime energy by an offset.

Authenticated **GET /energy/counters** exposes an allowlisted comparison for each paired plant: profile, solar selection, read timestamp, source-power freshness, `powerReadAt` and allowlisted `solarPowerW` components (`selfPvW`, `thirdPartyPvW`, selected `pvW`), `raw` selected-source kWh, `published` continuity-adjusted kWh and per-role status. It reads existing cached snapshots only and opens no Modbus connection. Host/IP, connection hashes, device identifiers, credentials and internal store data are omitted. This endpoint still contains private household energy measurements; keep responses private. A raw value can be present while its publication is withheld after a reset/source change. Counter status and timestamp determine whether it is current; numerical plausibility alone is not calibration.

The **Solar source (W and kWh)** selection also controls instantaneous `pvW` independently of whether the cumulative profile is enabled. Default **own PV** preserves existing behavior and does not probe 30194. **Third-party** uses only 30194; **combined** adds 30035 and 30194 exactly once. Both are distinct S32 signals in V2.9 table 5-1, printed pages 8 and 13 (PDF pages 16 and 21), gain 1000 kW (one raw watt). The additional read uses plant unit 247, the existing address offset and a one-second response timeout. Unsupported units, read failures, malformed/sentinel/out-of-range or negative selected components make solar power unavailable. A real zero is retained. No fallback to a partial sum or last valid value occurs; independently valid grid/battery reporting continues. Cached diagnostic components are not a new poll and may be stale: always check `powerReadAt` and `powerFresh`.

The selected watts feed the native solar companion, the original plant's `measure_pv_power`, Dashboard and newly sampled local `pvW`/`pvWh` history. Failed samples break the solar integration anchor, and reader/source changes break it before the new source starts. Old history is preserved without recalculation or backfill: earlier PV history may exclude third-party production. Grid-based demand history and Tibber meter references are unchanged. Solar generation alone is not unused surplus; this change supplies telemetry and does not add solar allocation, forecasting or coupled dispatch to the charging planner.

Upgrading preserves the existing selection, kWh fingerprints and acknowledgement counts. A plant already configured for combined/third-party kWh adopts that same boundary for W after upgrade; no new counter acknowledgement is required unless the source actually changes. Before selecting combined on another installation, compare simultaneous own and third-party readings with mySigen and verify that the installed firmware exposes distinct components. Firmware and AC/DC boundaries can differ; summing a signal that already includes third-party production would double-count it. Complete native house-flow validation across operating states remains in #37.

## Restart, reset and connection changes

The original plant stores per-counter raw and published high-water marks with `Device.setStoreValue`, **before** making a new value available to companions. A failed persistence write publishes no new counters. A normal app/Homey restart resumes from the saved marks without adding the lifetime total again. A monotonically increasing real source counter can cover an offline interval. Software checks reject negative deltas, backward time, epoch rollback and implausible jumps (10 MW over elapsed time plus a 1 kWh tolerance); these guards do not establish the inverter's actual rating.

A decreasing counter is withheld while the previous high-water mark stays intact. A single transient low read therefore cannot cause the following recovered reading to be counted twice. To resume after a **verified real reset**, increase **Counter reference generation / Räknarreferensens generation** on the parent plant (0 → 1, later 1 → 2, etc.). This is a local continuity acknowledgement, not a hardware reset. Each counter consumes a new generation on its next valid sample: it holds the last published total and uses the new raw value as the baseline, then adds only subsequent measured increments. Energy across that acknowledged transition is not guessed or backfilled. The published reading may consequently differ from the physical raw lifetime total by a fixed offset.

The same explicit acknowledgement is required after a detected connection/profile-binding change. Solar-only source changes use the separate acknowledgement above. Solar selection changes only its channel binding; unchanged grid/battery connection bindings remain compatible. The binding is a private hash of connection settings, not a verified device serial number: replacing equipment at the same address is not automatically detected. Confirm the correct plant/home and counter meaning before acknowledging. The effective solar generation is the sum of the shared and solar-only acknowledgement counts; both are non-negative integers and must not be reduced. Increasing the shared reference generation rebases every valid channel, so energy across that acknowledgement interval is conservatively omitted for all affected channels rather than guessed. Missing channels retain their old marks until their own next valid acknowledged sample. Reducing the generation is not a reset mechanism.

Device-store continuity survives ordinary app updates that preserve device data. It is **not included in the combined inverter/Tibber history backup**, which covers different stores. Uninstalling/deleting the parent, reinstalling or moving to another Homey requires separate handling of these device references and native Energy history; there is no automatic continuity-recovery claim for that case. Keep #6 open for broader backup/restore scope and physical testing.

## Verification and remaining acceptance

Automated fixtures cover manifest roles/pairing, source selection, signs and zero, invalid/stale/off-grid data, disable/re-enable, missing/removed sources, restart/stop, failed writes, serialized refresh and replacement during an in-flight write. Parent lifecycle tests verify that the shared source clears on communication loss/reconfiguration/shutdown. Tests also cover explicit solar power selection, combined/missing components, same-connection register/offset handling, propagation to Energy/plant/history and integration gaps on source changes. Tests also cover U64 decoding, exact register selection, high-water persistence, partial counter failures, restart, reset acknowledgement and kWh capability migration. Homey debug build validation checks the drivers; release checks must retain their runtime files/icons.

After review and release, record actual Homey firmware and mobile-client version, add the desired companions, inspect native Energy visibility and compare simultaneous readings/directions with mySigen. Check existing-meter exclusion, battery charging/discharging, solar/self-consumption/export, controlled connection loss and recovery, app/Homey restart and companion removal. Native kWh increments, counter/firmware support, reset handling and AC balance require physical verification after release; power visibility alone does not establish these checks. Publish only sanitized evidence. No physical inverter/counter verification is implied by Node tests or a successful build.
